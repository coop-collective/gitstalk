GitHub Actions live

Gitstalk runs the .github/workflows/*.yml you already have, unchanged, on Cloudflare Containers. A repository moved from GitHub keeps its CI and its deploys.

Where it stands. Live on the hosted service: a push that moves the stalk, Run workflow and schedules start runs; each job runs in its own fresh Cloudflare Container that is destroyed when the job ends; logs stream live to the Actions tab; secrets are masked; and jobs with id-token: write get OIDC tokens. A small Node CI job (checkout, setup-node, npm test) took about 20 s end to end on the hosted service. The dependency cache restores node_modules into memory between runs. Not yet: other caches and artifacts that outlive a job, the GitHub REST API through GITHUB_TOKEN, and runners other than Ubuntu; services: and container: are not yet verified on the hosted service.

When workflows run

GitHub event On Gitstalk First release
push to main The stalk moved. main and your base branch name it, so branches: [main] keeps working. yes
workflow_dispatch A button or an MCP call, with typed inputs. yes
schedule Cron in UTC, at least 5 minutes apart, read from the stalk. yes
pull_request A bean was pushed. It runs on the bean squashed onto the sprout, which is GitHub's merge ref. later
merge_group The sprout's validation. later

A new [actions] table in checks.toml will say which jobs are required to land a bean or to move the stalk, the way branch protection does; other jobs are advisory.

Compatibility report

Workflows are parsed with GitHub's own parser and expression library. Every file gets a report that marks each feature as runs, runs differently (with the difference) or never runs here (with the reason). It shows on the workflow page and in the push of the bean that changes the file.

  • Runs: jobs, needs, if, outputs, matrices (up to 16 legs), run steps, JavaScript and composite actions, concurrency, timeout-minutes, permissions, secrets and vars. Unmodified actions/checkout works against Gitstalk.
  • Runs differently at first: actions/cache of node_modules or a package-manager store, and actions/setup-node with cache:, become the dependency cache; other caches and artifacts last one job, not across jobs; environment: approvals are ignored and the report says so.
  • Not at first: Docker actions, container: and services:; reusable workflows; runs-on other than ubuntu-latest or ubuntu-24.04.
  • Never: events for objects Gitstalk does not have (issues, releases), and pull_request_target, refused on purpose.

Secrets and variables

  • Repository secrets are encrypted at rest, write-only (Settings lists names, never values), injected only into the steps that name them, and masked in logs.
  • Org secrets work the same way and reach all of the org's repositories, only its private ones, or the ones you pick. Org owners and admins manage them in the org's Settings, Secrets and variables. A repository secret with the same name wins over the org's, as on GitHub.
  • Variables (${{ vars.NAME }}) are plain configuration at repository and org level, with the same access choices for org variables. Anyone with a role sees their values and logs print them unmasked, so never put a credential in one.
  • Repository Settings shows the repository's own secrets and variables and the org ones it inherits, read-only, with where each comes from. People with a role see secret names, never values; maintainers and the owner change them.
  • Stalk, dispatch and schedule runs get the secrets they name. That is how deploys work.
  • Pre-land runs of a bean pushed by an agent session, a deploy token or a collaborator below maintain get no secrets and a read-only job token, like a fork's pull request on GitHub. A per-secret toggle, available to pre-land checks (off by default), lets a low-risk test key through. Never use it for a deploy credential.
  • To keep agents from changing the code that holds the secrets, list .github/** in protected_paths of checks.toml: then only maintainers and the owner, pushing with their own personal token or SSH key, may change workflows. Protecting workflow files by default comes later.
  • A stalk workflow still runs code that agents wrote (your package.json scripts) with its secrets, as auto-merge does on GitHub. Approval before secrets are released comes later.

From an agent rolling out

An agent connected over MCP drives the same loop you do on the web, with plain tools and your role on the repository:

  1. It pushes a bean that adds or changes .github/workflows/deploy.yml. When the bean reaches the stalk, that is a push to main, and the workflow runs.
  2. actions_wait_for_run with the bean holds until the runs its landing started finish (at most 30 minutes per call), then answers each run's conclusion and, for a failure, the failing step and the last lines of its log.
  3. actions_job_log reads more of a job's log (the newest lines, or only the lines matching some text), with secrets already masked.
  4. The agent fixes the cause in a new bean, pushes and waits again.

actions_dispatch, actions_rerun (the whole run again, same commit and inputs), actions_cancel and automation_run need the maintain role and the agent's write scope. A deploy token such as CLOUDFLARE_API_TOKEN is best added by you in Settings → Secrets and variables; the agent sees its name with actions_secret_list. If you give the agent the value instead, actions_secret_set stores it, write-only, when you are a maintainer and ticked the secrets scope; the audit log names you and the agent's client.

Job token and OIDC

Each job gets a short-lived token bound to its repository, revoked when the job ends. With contents: write it may push bean/* branches only, so code a job writes still goes through the pre-land check. With id-token: write, jobs get GitHub-shaped OIDC identity tokens from a Gitstalk issuer, so aws-actions/configure-aws-credentials and Google's and Azure's equivalents work once you register the issuer. Pre-land runs of untrusted beans get no identity token by default, and if a repository opts in, their subject is distinct so no existing trust policy matches it.

Dependency cache live

Each run restores node_modules from the repository's last snapshot into memory, so installs start from a full tree instead of the registry. On the hosted service, a fastify job (146 MB of dependencies) with an unchanged lockfile restored in 1–3 s and npm ci took under 1 s; the whole job took about 20 s, against about 2 min 45 s for the same job without the cache in the same push, where npm ci from the registry took about 2 min 20 s. On a test stack, with npm ci --no-audit, the restore took 1–3 s against 6–14 s for npm ci from the registry, on fastify and on a Next.js-class app (533 MB). The first run and a lockfile change are slower than without the cache by the time it takes to save the new snapshot at the job's end (about 9 s for fastify on the hosted service). Every run is in the design write-up.

  • Automatic for workflows that already ask for a cache: actions/setup-node with cache: npm, pnpm or yarn (its cache-dependency-path names the directory), and actions/cache whose every path is node_modules or a package-manager store (it keeps its id, and cache-hit is true on an exact hit). Nothing to change in the file.
  • Opt-in for other workflows: a step uses: gitstalk/deps-cache@v1 after checkout, with working-directory if the lockfile is not at the root. The name from before the rename, beanstalk/deps-cache@v1, works too.
  • node_modules lives in memory (a tmpfs), never on the container disk. The snapshot key is the lockfile plus the install directory, platform, Node and package-manager versions and the install flags; another lockfile restores the closest snapshot and the install brings it up to date.
  • With npm ci: after an exact hit the tree is exactly what npm ci would build, so npm ci keeps it and only runs your package's own install scripts. After a lockfile change npm ci runs as usual (it deletes node_modules first), and the save uploads only the chunks that changed. pnpm install, yarn install and npm install update a restored tree in place.
  • Only runs of the stalk save snapshots. Pre-land, dispatch and schedule runs read them and never write, so a bean that has not landed cannot change what a later stalk run installs. Snapshots belong to one repository and are never shared.
  • Turn it off with the repository or org variable GITSTALK_DEPS_CACHE=off; change the snapshot cap with GITSTALK_DEPS_SNAPSHOT_MAX (for example 2GiB). A variable set under its name from before the rename (BEANSTALK_*) is read when the GITSTALK_* one is absent; saving the Actions settings moves it over.
  • rolling out Deleting a repository deletes its snapshots, its Actions logs, secrets and variables, and stops its schedules.

npm audit in installs rolling out

Jobs run npm with NPM_CONFIG_AUDIT=false and NPM_CONFIG_FUND=false, so npm ci and npm install skip the audit npm otherwise runs inside every install. It never changes what is installed, but it is slow: for fastify's lockfile it took about 90 s of a 97 s npm ci, against about 10 s without it. To keep it, set the repository or org variable GITSTALK_NPM_AUDIT=on, set NPM_CONFIG_AUDIT in the workflow's env:, or run npm audit as its own step. The measurements are in the design write-up, section 12.

Limits on the managed beta

Actions minutes 100 per repository per month
Job timeout 60 minutes
Concurrent jobs 4 per repository
Log retention 30 days
Dependency snapshot (compressed) 4 GiB, a repository or org setting
Dependency snapshots per repository 10 GB, unused for 7 days are deleted
Memory for node_modules 6 GiB of the job's 12 GiB

Minutes count only while a job runs. A container kept warm for the next job of the same repository (coming soon) is not counted. A repository that has used its minutes gets a clear "monthly minutes used" refusal, never a red run. When you self-host, you set every one of these.
