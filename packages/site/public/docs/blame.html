Why this line: blame by bean beta

With dozens of changes landing an hour, git blame points at a commit nobody can read. Gitstalk points at the bean: the change, and the one-sentence reason it was made. Ask before you edit a line and you learn what you would be undoing.

Status

The why_lines tool and the history behind it were merged on 14 October 2026 and are beta until the hosted deploy is confirmed. The blame column in the web explorer is live; it is computed a different way and shows less (see In the web app).

The problem with git blame here

A line's last commit in a busy repository is usually a squash made by the engine or a revert. The author is an agent, and the message was written for the engine. What you want to know is:

  • Which bean changed this line, and what was it trying to do?
  • Did a person weigh in through a decision card?
  • Was that bean taken back later, so the line really belongs to an older one?

In the web app

On the Ask tab, before you ask anything, choose Browse all files, then ask the Files explorer a who or why question, such as "who changed tax rounding and why?". It opens the first matching file with a column that names the bean that last changed each run of lines, linked to the bean, with its landing number. Lines older than the first landing show as base.

How agents use it

Before editing, an agent calls why_lines. Omit start and end for the whole file. ref is sprout (the staged line, the default) or stalk (the stable line). Needs the read scope; see MCP tools and scopes.

Tool call
why_lines { "repo": "acme/shop", "path": "src/tax.ts", "start": 1, "end": 5, "ref": "sprout" }

The answer (shortened, with illustrative values):

{
  "path": "src/tax.ts", "ref": "sprout", "lines": 5,
  "ranges": [
    { "lines": "1-2", "bean": "round-tax-lines",  "commit": "9c1e4a7b02", "kind": "landing" },
    { "lines": "3",   "bean": "half-up-rounding", "commit": "41d0be3c88", "kind": "landing" },
    { "lines": "4",   "bean": null, "commit": "0a77f2e9d1", "kind": "base", "title": "Initial import" }
  ],
  "beans": {
    "round-tax-lines":  { "title": "Round tax per line, not per cart", "actor": "ada", "decisions": [], "reverted": false },
    "half-up-rounding": { "title": "Round half up", "actor": "claude-code", "decisions": ["D-3"], "reverted": false }
  },
  "history": [
    { "commit": "41d0be3c88", "kind": "landing", "bean": "half-up-rounding", "change": "modified", "at": "2026-10-14T09:12:00Z", "on_stalk": true }
  ],
  "summary": "2 beans last changed these lines: round-tax-lines, half-up-rounding. Read their titles and decisions before changing them."
}
  • Per range: the bean, its landing commit and the kind of commit (landing, revert, reset, base or an ordinary commit).
  • Per bean: its title (its intent), who pushed it, the decision cards that named it and whether a later revert took it off the sprout.
  • Path history: the recent landings and reverts that touched the file, newest first, and whether each is on the stalk.
  • Reverts give lines back. If a bean was reverted, its lines go back to the beans that wrote them before, and later beans keep their own lines.

Pair it with the other read tools

work_overlaps tells an agent who is editing the same files right now; why_lines tells it who changed them before. Together they let it fit its change to the intents around it.

Edit and read with no checkout

Two tools are companions for an agent that has no clone. repo_read reads files, lists trees and greps code; bean_commit sends the changed files and Gitstalk builds the commit. Both are beta. See MCP tools and scopes for limits and the conflict answer.

How it is computed

Gitstalk keeps a derived history beside each repository's engine. It follows the sprout's landings in order, classifies each from the trailers the engine writes (Task: for a landing, Reverts: for a revert), and records which commit last changed each span of lines in each file.

Each kind of history has a version, and when the code's version changes the rows are dropped and computed again. Some kinds update when a landing is reported, others when someone first asks, so a read always answers from up to date rows. The design is in docs/claude-opus/34.

Limits and what is not done

  • History begins at the repository's first commit, or at most 256 commits back. Older lines show as base.
  • Bean branches are not derived; ref is sprout or stalk.
  • A file that is binary, over 256 KB or past the first 200 files of a change is owned whole by the commit that changed it.
  • The web file view does not show the bean's title, decisions or reverts yet; only the tool does. Showing "why" in the web view is not built.
  • work_overlaps was not moved onto this history (the overlap index is planned), because most of its answer is about beans still in flight.
