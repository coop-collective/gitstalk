Architecture

A merge queue makes every change wait for the ones in front of it. Gitstalk checks each change on the exact tree it would land on, lands it at once, and validates the stable line behind it. This page explains the rules that make that safe, the Cloudflare pieces it runs on, and what we measured.

The path of a bean

  1. Pushed

    An agent pushes bean/<name>. The gateway checks the credential, refuses anything that is not a bean inside the git protocol, forwards the pack to storage with a token the agent never sees, and hands the bean to the repository's engine. A plain push returns in seconds and the agent takes its next task.

    WorkersArtifacts

  2. Pre-land check, in the author's own sandbox

    The runner squashes the bean onto the current sprout and runs the whole suite on that exact merged tree, in a sandbox leased for this bean alone. If it is red, the bean goes back to its author with the failing tests and the landed beans it collided with.

    ContainersDurable Objects

  3. Landed on the sprout

    A green bean lands at once, and every other bean builds on it from then on. If the sprout moved during the check, the engine re-checks only when the risk calls for it (below).

    Durable ObjectsArtifacts

  4. Validated

    Asynchronously, CI validates the sprout's newest commit. At most a window of landings may run ahead of validation.

    Containers

  5. On the stalk

    A green validation moves the stalk to that commit, together with every bean below it. The stalk never moves to anything that has not passed.

    ArtifactsQueuesD1

The engine's rules, and why each one is there

Every rule below was added because a measured run needed it; most were measured on and off. The engine is one SQLite-backed Durable Object per repository, so every decision about a repository is made by one writer, in order.

Check the exact tree, before landing

The original idea was to land first and fix forward. With real agents it collapsed: repairs cost about 7 times a task, and with 12 Sonnet agents only 2 of 40 tasks went green in 40 minutes. Checking the merged tree before landing, and handing a red back to its author, took the red trunk away entirely. Releasing the author while its check runs is what keeps agents busy.

The sprout window

When agents were released during their checks, landings came in bursts (19 in one minute) and validation fell 27 commits behind. Now at most W landings may run ahead of validation: W starts at 8, grows by 2 with each green validation, halves on a red one, and stays between 2 and 16. It held landings to about 6 a minute and took that race from 24 to 34 green tasks. It also bounds how much work any red can touch.

Check reuse

A bean that lands on the very commit its pre-land check passed needs no second run of the same suite on the same tree: that commit is green without CI. On staging this replaced 7–8 of about 22 validations per race.

Revert first, then reset the red window

A red validation is confirmed by the same test failing twice, so a flake never reverts a good bean. When one bean is the only suspect, it is reverted at once. Otherwise the engine resets the sprout: one new commit takes the stalk's tree (it never conflicts and nothing moves backwards), and every bean in the window re-runs its pre-land check and lands again, suspects one at a time. At 30 agents an unrevertable break once held the sprout red for about 20 minutes; with the reset the sprout is green again about 1.3 minutes after a red, and in simulation the 35th green came 10 minutes sooner.

Informed repair, then reconcile, then decide

A red resumes the author's own session with the failing tests and the intent and diff of the bean it collided with. A repeated red goes to a reconcile step, and only a genuine contradiction becomes a decision card, with the bean parked so it never holds a run open.

Structural merge, re-checked

When git's line merge conflicts on code files, the runner retries with a structural merge (Mergiraf, run as a separate binary) on just those paths. A structurally merged tree was never checked as such, so it is always re-checked before it lands. The 30-agent results below use this rule.

Dependency-aware starts

With a task list, a free agent takes a task that clashes with nothing in flight, longest dependency chain first. On 12 agents, the full rule set with first-in, first-out starts shipped more but was slow; dependency-aware starts are what turned it into a win. In simulation with 200 tasks in dependency chains, 200 shipped against 173. This applies where Gitstalk schedules the work (races, backlogs); pushed beans are taken in arrival order.

On-demand pre-land capacity

Each bean in check gets its own sandbox from a shared pool, up to 32 per repository. Waiting for a sandbox never counts against the suite's time limit, and a timeout is never reported as a red. Before this, pre-land checks shared two sandboxes, and 16 parallel workers collapsed (what happened).

The Cloudflare pieces, and why

Product What runs there Why it fits
Workers The gateway (git proxy, engine host, RPC), the web app, the MCP server, the SSH front. Stateless, close to every agent, talking to each other by service-binding RPC rather than HTTP.
Durable Objects One engine per repository; the runner pool; per-run stream objects; SSH connections; Actions runs. A single writer per repository makes landing decisions serial without locks, with SQLite storage beside them and alarms for timers.
Containers The Rust runner (squash, merge, revert, run the suite in a network-isolated sandbox), the SSH server, and Actions jobs. Real git and real test suites need Linux. A container per check gives each bean a clean, exact tree.
Artifacts Every repository's git storage. Git hosting without servers. It has no server-side merge, which is why merges happen in the runner.
D1 Accounts, the repository registry, access, the activity index. These are cross-repository reads (an owner's list, a name lookup). A single registry object would serialise every page load.
Queues Engine events to the D1 index. The engine sends from a cursor over its own log and the consumer is idempotent, so nothing is lost; the index runs about 3 s behind.
KV OAuth grants and tokens for MCP. What the OAuth provider library uses.
R2 Actions logs. Logs never sit in a container or a Durable Object.
Dynamic Workers Automations (coming). Isolates that start in milliseconds, with no network unless granted.
Workers AI Ask: a small decision model picks which view answers a question. Picking a view takes about half a second; generating a page would not.

The git proxy and identity

  • Agents never hold storage tokens. The gateway mints a short-lived Artifacts token per request inside the engine and streams the request through; the client's own credential never goes upstream.
  • Landing is never a permission. No token, key or role can push to the sprout or the stalk. Only the engine moves them.
  • One access rule decides HTTPS git, SSH git, MCP and the web: a person's role, capped by the credential's scopes. A repository you may not see is a 404 everywhere.
  • People sign in with passkeys or a six-digit email code (sent through Cloudflare Email Service, stored only as a keyed hash). Agents connect with OAuth 2.1 (dynamic client registration, PKCE). Tokens and sessions are stored hashed. No third-party service sits in any request path.

What we measured

Against GitHub's merge queue, on real changes

The same 38 merged pull requests from fastify's history, each with its own tests, pushed in parallel to a GitHub repository with GitHub's merge queue and Actions, and to a Gitstalk repository. CI capacity was matched: 20 pre-land checks at once (the GitHub organisation's concurrent Actions jobs) and 2 validations at once (the queue's build concurrency). The pushes were replayed on a schedule fitted to real agent runs, without models.

GitHub's queue slows as more work arrives, because it builds two groups at a time; Gitstalk keeps landing each change in about a minute, so the gap grows with parallelism. With 16 workers Gitstalk landed about 3× as many changes per 10 minutes. Every run landed all 38 changes correctly on both forges.

With real agents organising the work

One Claude Code lead with Sonnet worker subagents got the whole backlog on each forge and decided splitting, ordering and retries itself. At 4 workers the forges tied: the agents were the bottleneck. At 8 workers Gitstalk's last task went green at 22 minutes against GitHub's 41 (about 2×), and the median change integrated in 1.0 minute against 5.4.

The synthetic 30-agent arena

30 Claude Code agents (Sonnet) worked 40 tasks that collide on purpose, on three seeds, against a batched merge queue we built to behave like GitHub's. Gitstalk shipped 39–40 of 40 against the queue's 34–35, reached its 30th green task 1.7–2.3× sooner and finished 1.3–1.6× sooner, with no red stalk check and the same agent spend ($13.31 against $13.20 over the three seeds). Cloudflare infrastructure cost about $0.40 per Gitstalk race.

Read these with care.

  • The 4- and 8-worker fastify rows are one seed each; the arena is three seeds, one run each, and seeds swing a lot.
  • CI minutes are not like for like: GitHub's include runner setup and npm ci.
  • The arena's tasks are short and synthetic; with 7× longer tasks the lead shrank to 1.3–1.4×. Its queue is ours, not GitHub's.
  • The orchestrated races are one run each. Agents ran on a laptop; only the forge ran on Cloudflare.
  • Earlier harness versions favoured Gitstalk; how much, and the fix.
