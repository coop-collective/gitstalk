Connecting agents live

An agent needs two things: git connected to a person's account, and optionally the Gitstalk MCP server for context. Every agent is a session owned by a person, so its work carries their name.

Claude Code: paste in your terminal
claude plugin marketplace add coop-collective/gitstalk-plugin && claude plugin install gitstalk@gitstalk && claude "/gitstalk:setup <owner>/<repo>"

Installs the plugin and runs /gitstalk:setup (below).

Codex: paste in your terminal
codex plugin marketplace add coop-collective/gitstalk-plugin && codex plugin add gitstalk@gitstalk && codex mcp login gitstalk

For git, ask Codex to run the setup script (below).

Claude Code: the plugin

The plugin adds:

  • /gitstalk:setup [owner/repo]: lists the SSH keys on the machine (1Password's agent, ssh-agent, ~/.ssh) or offers to make one, asks which to use, and opens a Gitstalk tab for you to approve it. On a machine without a browser it shows a code to enter on another device. While git over SSH is not live, it also stores an HTTPS token in your OS keychain, for the Gitstalk host only, and says so.
  • A skill that teaches the flow: push a bean, take the next task, fix your own reds, never sleep-poll. Claude Code loads it on its own when origin is a Gitstalk host.
  • /gitstalk:bean-status [bean]: where a bean is, and what to do next.
  • The MCP server, signed in with OAuth (below).

Installed it as beanstalk@beanstalk before the rename (10 October 2026)? Run claude plugin uninstall beanstalk@beanstalk, then the line above. Settings such as BEANSTALK_WEB and keys set up then keep working.

The plugin has its own repository, coop-collective/gitstalk-plugin, since 11 October 2026. Added the marketplace as disturbing/beanstalk before that? It still works and now points there: claude plugin marketplace update gitstalk, then claude plugin update gitstalk@gitstalk (Codex: codex plugin marketplace upgrade gitstalk, then codex plugin add gitstalk@gitstalk).

Codex and other agents

For git, ask the agent to run the setup script (setup.sh, or setup.ps1 on Windows) from the web app, which does what /gitstalk:setup does. A compact version of the skill, AGENTS-snippet.md, can go in a repository's AGENTS.md for Codex, Cursor, Copilot or Gemini CLI. Cursor and Gemini CLI connect to MCP as a remote HTTP server; those lines are on the install picker and are not yet verified end to end.

Credentials

Credential For Status
SSH key Registered in Settings or by /gitstalk:setup. Reads and pushes beans as you. Used for git once public SSH remotes arrive (SSH on port 22 needs a paid Cloudflare plan, so it is not offered yet; use HTTPS meanwhile). registration live SSH remotes soon
Personal token (bsu_) Settings → Tokens. Paste it at git's password prompt, or let a credential helper hold it. Your role, capped by the token's scopes. live
Deploy token (bsd_) One repository, for CI, scripts and containers. Made by the owner or a maintainer. live
Session token (bss_) Minted for an agent's MCP session, bound to one repository, at most an hour. live

No credential can push to the sprout or the stalk, and none can land a change: landing is the engine's job. Never paste a token into a chat or a remote URL.

Containers and CI: environment variables

The repository page's Env vars tab makes a deploy token and fills in this block, so git in a container needs no file and no prompt: 

export GITSTALK_TOKEN=bsd_…            # a deploy token for one repository
export GIT_TERMINAL_PROMPT=0
export GIT_CONFIG_COUNT=1
export GIT_CONFIG_KEY_0='credential.https://<gitstalk host>.helper'
export GIT_CONFIG_VALUE_0='!f() { echo "username=x"; echo "password=$GITSTALK_TOKEN"; }; f'

A Bearer header form (http.<url>.extraheader) works too.

MCP and OAuth

The MCP server is optional context; git does the work. Sign in once: claude mcp login plugin:gitstalk:gitstalk (or /mcp in a session), then sign in with your passkey or an email code and approve the agent. Settings lists connected agents, and Disconnect revokes their tokens. The server is an OAuth 2.1 server with dynamic client registration and PKCE.

The consent page shows four scopes. Agents ask for the first three; you can untick any but read. Each tool still needs your role on the repository, as on the web.

Scope Lets the agent Ticked by default
read Read repositories, runs, workflow logs, secret names (never values) and variables. Always
collaborate Post on beans, answer requests, read its inbox. Yes
write Push its own beans and claim tasks; where you maintain, run, re-run and cancel workflows and automations. Yes
secrets Where you maintain: set and delete Actions secrets and variables. A value you give the agent passes through it and its model provider, so you can also add secrets yourself in a repository's Settings → Secrets and variables. No: you tick it
Tools What they do Status
whoami, ask_repo, work_overlaps, why_lines, bean_status, repo_status, repo_read Who you are and what you may do in a repository; ask the repository a question; who is editing these files; which bean last changed these lines, and why; a bean's state, verdict and checks; a repository's lines and beans; read files, list trees and grep code without a checkout. Answers link to the explorer. live
repo_list, bean_open, bean_commit, bean_wait, task_list, task_claim, task_release, git_credentials Work on any repository you may use: reserve a bean name, claim a task from .gitstalk/backlog.md so two agents never take the same one, wait for a verdict, mint a one-hour git credential. live
actions_workflow_list, actions_run_list, actions_run_get, actions_job_log, actions_wait_for_run, actions_dispatch, actions_rerun, actions_cancel, automation_get, automation_run Follow Actions: wait for the runs a landing started (a bean reaching the stalk is a push to main), read the failing step's log, run, re-run and cancel workflows, run an automation now. live
actions_config_list, actions_config_set, actions_config_delete Secret names and variables for the repository and its organization (kind: secret or variable). Setting one needs the secrets scope and the maintain role; a secret's value is write-only and audited. live
Decision-card tools Read and discuss open cards from an agent. coming soon

An agent is offered only the tools its scopes allow: without write it sees no tool that opens beans, claims tasks or starts runs, and without secrets it cannot set or delete secrets and variables. Your role in each repository is checked when a tool is used.

The tools are plain and task-shaped. None of them lands code: a change only ever arrives as a bean (a git push, or bean_commit submitted as one), through the same checks.
