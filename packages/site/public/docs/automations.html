Automations live

An automation is an agent defined by a file in .gitstalk/automations/. It runs when something happens in the repository, on a schedule or by hand. Each run gets a fresh container with the repository checked out, the event as context and a memory of its own that persists between runs, and it may propose fixes as beans. Live on the hosted service since 9 October 2026.

Files, not database rows

The definitions live in git. Each time the stalk moves, Gitstalk reads the automation files at the new head, checks them and rebuilds its index of triggers and schedules. A file with a problem is listed on the repository's Automations tab with the line and the reason, and does not run. So changing an automation is a bean like any other: it goes live when the stalk takes it. To keep agents and writers away from them, list them in protected_paths of .gitstalk/checks.toml (for example .gitstalk/**): then only maintainers and the owner may change them, with their own credentials or the builder below.

Gitstalk was called Beanstalk until 10 October 2026. Automations in .beanstalk/automations/ keep running and are listed beside those in .gitstalk/automations/; when both folders hold a file of the same name, the one in .gitstalk/ wins. The builder saves new automations to .gitstalk/automations/ and edits a file where it is. Runs set every GITSTALK_* variable also as BEANSTALK_*, and the event payload carries the same object under gitstalk and beanstalk, so older scripts keep working.

An example

# .gitstalk/automations/fix-red.yml
name: Fix red beans
on:
  bean_red:                     # a bean's pre-land check went red
  schedule: [{ cron: "0 9 * * 1" }]
permissions:
  beans: write                  # may push fix beans as itself
max-cost-usd: 0.50
prompt: |
  Read why the bean went red. Check your memory for this failure.
  Fix it in a new bean and note what you tried and learned.

A .md file works too: YAML front matter between --- lines, and the body is the prompt. Every automation can also be run by hand from its page.

Building one in the browser rolling out

New automation on the Automations tab starts from a template (Fix red beans, Weekly dependency bump, Summarize landed work, Triage decision cards, a shell heartbeat, or blank), and Edit opens an existing one. The builder is a form beside the file's YAML, kept in sync both ways: change a field and the YAML changes by that line only, with your comments and layout kept; edit the YAML and the form follows. Every change is checked by the same rules Gitstalk uses when it reads the file, with problems shown at their field and line. Schedules show in words with their next run times.

  • Saving is a bean, never a push to main. Gitstalk commits the file in your name on the latest landed version and pushes it as bean/automation-<name>-<id>. The builder follows it: checking, then saved with a link to the commit, or red with the reason. You need the write role, or maintain if checks.toml protects the file.
  • Edited by someone else meanwhile? The builder merges field by field. Changes to different fields merge, and it shows you the result before saving ("merged with @dana's change to the schedule"). Where you both changed the same field, it shows theirs and yours side by side to pick or edit. Your draft is also kept in your browser until it is saved.
  • Delete is a bean that removes the file, after you confirm.
  • Test run (maintainers and the owner) runs the draft once by hand without saving it, and never writes its memory.

Triggers

on: When
bean_opened, bean_landed A bean is pushed; a bean lands on the sprout
bean_red A bean's pre-land check is red, or it conflicts
bean_parked, bean_dropped, bean_reverted A bean waits for a person, falls off, or is taken off the sprout
stalk_moved, stalk_reset, validation_red The sprout is promoted to the stalk; the stalk goes back; a validation is red
decision_opened, decision_decided A decision card opens; it is answered
schedule, workflow_dispatch Cron in UTC, at least 5 minutes apart; by hand (always available)

Bean events take beans: and authors: filters with GitHub's glob rules. An automation never fires on its own beans, and runs one at a time: a trigger that arrives while it runs waits, and a newer one replaces it.

What a run gets

  • A container of its own, the same as a GitHub Actions job: Linux, git, Node and Python, the repository checked out at the stalk, and the event in $GITHUB_EVENT_PATH. It is destroyed when the run ends.
  • Memory: a directory restored from the git ref refs/automations/<name>/memory and committed back at the end, so every run's notes are a commit you can read, diff or revert. Anyone who can read the repository can read it.
  • An agent with shell, file and git tools, on a Workers AI model (@cf/moonshotai/kimi-k2.7-code by default) through AI Gateway. The container never holds a model key: its calls go through Gitstalk, which applies the run's and the repository's spend caps. The builder calls this harness Prompt, written as harness: agent (the default). Shell, written as harness: shell, runs a script instead, with no model.
  • Its own identity, <name>[automation]. With permissions: beans: write it may push bean/*; those beans go through the pre-land check like anyone's, and it can never push to the sprout, the stalk or main.
  • Secrets it names in secrets:, by the same rule as Actions: scheduled and manual runs get them; runs started by a bean event get only the secrets marked available to pre-land checks, because the event carries text that anyone with push access wrote. Values are masked in the log.

Limits

Limit Hosted beta
Run timeout 30 minutes by default, at most 60
Container minutes Shared with GitHub Actions: 100 per repository per month; waiting is free
Model spend $0.50 per run by default (at most $5), $10 per repository per month
Memory 50 MiB

On the Automations tab

The repository's Automations tab lists each automation with its triggers, what it runs, who it acts as, its memory ref, its limits and any problems in its file, and a Run button for maintainers. A run's page streams the agent's turns live and shows what it did: the beans it pushed, its memory before and after, and its model calls and spend. Logs are kept for 30 days.

Not yet: Gitstalk tools for the agent (comments, decision cards), your own model keys or other agents such as Claude Code, webhooks into an automation, and a browser editor for .github/workflows files.
