# 32. Approval rules by kind of change

Built 2026-10-14. Motivation: Anthropic's "Redesigning source control at Anthropic" (Scion), which describes review tooling with semantic approval rules that tell comment-only changes apart from sensitive logic changes, and access control per directory (paraphrased). Here a repository says, in one file on its stalk, which kinds of change land on their own, which Clef triages and which wait for a person; classes are computed by code, never by a model, and every routing leaves a receipt.

Code: `packages/shared-race/src/policy-file.ts` (file format, parse, JSON Schema), `approval-policy.ts` (classes, routes, receipts), `code-tokens.ts` (the comment-only lexer); `packages/gateway/src/approval/` (the gate, its store and host, the Clef adapter, the Settings RPC); `packages/web/app/[owner]/[repo]/settings/rules` and `components/rules/`; approving: `shared-race/src/bean-approval.ts`, the gateway's `approval/approve-rpc.ts`, `approve-bean.ts`, `bean-hold.ts`, `self-approval.ts`, the web's `components/repo-tabs/held-panel.tsx` and `src/server/approval-actions.ts`, MCP's `tools/bean-approve.ts`.

## 1. The file: `.gitstalk/policy.yml`

```yaml
# yaml-language-server: $schema=https://gitstalk.dev/schemas/policy.json
groups:
  security: ['@alice', '@bob']
classes:
  - name: comment-only
    match: { syntax: comments-and-whitespace }
    route: auto
  - name: docs
    match: { class: docs-only }
    route: auto
  - name: migration
    match: { paths: ['src/db/migrations/**'] }
    route: card
    reviewers: ['@data']
  - name: protected
    match: { paths: ['src/auth/**'] }
    route: card
    writers: ['@security']
  - name: api
    match: { paths: ['src/api/**'] }
    route: triage
  - name: everything-else
    match: { otherwise: true }
    route: triage
```

- `classes[]`: `name` (lower-case, dashes, unique; `policy-change` is built in), optional `description` (a sentence, at most 200 characters; Clef reads it when it triages the class's beans), `match`, `route`, optional `reviewers`, optional `writers`.
- `match` is one of `{ paths: [...] }` (any changed file matches a pattern; the patterns are `protected-paths`' glob, `24-checks-config.md`), `{ syntax: comments-and-whitespace }` (every changed file differs only in comments and whitespace), `{ class: docs-only | tests-only | lockfile | comment-only }` (a built-in class, below), or `{ otherwise: true }` (the fallback class, below).
- **The fallback class** (`match: { otherwise: true }`, owner's decision 2026-10-14): it applies only when no other class matched, so "everything else triage" no longer needs a list of source roots. At most one class may be the fallback, and `otherwise` cannot be combined with `paths`, `syntax` or `class` (each refused with its line and column; `otherwise` must be `true`). Chosen over a top-level `otherwise: { route: triage }` key because the fallback stays an ordinary class: it has a name on receipts and push lines, a `description` Clef reads, `reviewers` and `writers`, and the JSON Schema offers it as one more `match` shape.
- `route`: `auto` (lands and promotes as before), `triage` (Clef picks `auto` or `card`), `card` (held until a person approves).
- Principals: `@handle` (a person; a push acting for them, by any credential), `@group` (a name under `groups`, which wins over a handle of the same name), `agent:a<slot>` (a race's agent slot).
- `.beanstalk/policy.yml` is read when `.gitstalk/` has none (`config-dir.ts`). No file: every bean is `auto`, exactly as before, and pushes show no rules lines.

**Format decision (owner, 2026-10-14): YAML, not TOML and not a section of `checks.toml`.** Automations are already `.gitstalk/automations/*.yml` in GitHub Actions syntax, and GitHub's repository-config convention is YAML (dependabot.yml, labeler.yml, workflows). `checks.toml` stayed as it was then; the same day the checks moved to YAML too (`.gitstalk/checks.yml`, `24`), so all `.gitstalk/` configuration is YAML now and both files share one strict parser (`strict-yaml.ts`). Parsing is strict: the `yaml` package (catalog 2.9.1) with YAML 1.2 core schema (`no` stays a string), unique keys, and anchors, aliases and merge keys refused, then Zod in `checks-config.ts`' style. Every problem carries line, column and field; `POLICY_JSON_SCHEMA` is generated from the same Zod schema (`z.toJSONSchema`) for the `yaml-language-server` first line. Property tests: every valid policy written by `writeApprovalPolicy` reads back equal; no input throws.

A separate file rather than keys in the checks file also matches where each is read: checks come from the tree being checked (a bean may change its own suite under `protected-paths`), the rules come from the stalk (a bean never changes the rules that judge it).

## 2. Classes, computed by code

- **Built in, for every bean:** `docs-only` (every file is `*.md|mdx|markdown|txt|rst|adoc` or under `docs/`), `tests-only` (under `test/`, `tests/`, `__tests__/`, or `*.test.*`, `*.spec.*`, `*_test.*`, `test_*.py`), `lockfile` (every file a package manager's lockfile), `comment-only` (below). Each holds only when every changed file has the kind.
- **`comment-only`** (`code-tokens.ts`): each side of each changed file is lexed into code tokens with `//` and `/* */` comments and whitespace dropped, keeping string, template (with `${}` nesting), regular-expression and Rust raw-string, char and lifetime literals whole; the streams must be equal. Judged for TypeScript and JavaScript (not JSX, where `//` can be text), Rust, C and C++, Java and Go. Every doubt is "not comment-only" (an added, deleted, binary or unknown file, anything unterminated, files over 512 KB; punctuation runs are kept whole, so `a+ +b` never equals `a++b`, at the price of calling a `)+(` → `) + (` reformat code). File contents are read (one Artifacts diff of the merge) only when the policy has a syntax class and every changed file is in a judged dialect.
- **`policy-change`:** any change under `.gitstalk/` or `.beanstalk/` except `backlog.md` (agents tick tasks with ordinary beans) is routed `card` whatever the file says, when it comes from an agent. When the push is a person's own and they may decide (owner or maintainer, personal token, SSH key, or the web's Settings editor), the push is the decision: the class is listed and the other classes route it. The policy file is also always protected (`ALWAYS_PROTECTED` in `checks-config.ts`, next to the checks file), so only those people can change it at all.
- **Route:** the strictest matched class wins (card over triage over auto). A comment-only change takes the route of the policy's comment-only class when it has one, even in a sensitive path: no behaviour changed. Writer limits always apply.
- **Fallback:** when no other class matched, the fallback class matches, and its route, reviewers and writers apply (it is the deciding class, so a triage shows Clef its description). It never applies when another class matched (a property test checks the classification with and without it), never to an agent's policy change (`policy-change` still wins), and never to a change with no file outside `.gitstalk/` and `.beanstalk/`, so a decider's own save from Settings and an agent's backlog ticks land as before. The built-in classes (`docs-only` and so on) count as matched only when a policy class names them: in a policy without a docs class, a docs-only change takes the fallback's route.

## 3. Where it runs, and why

In the gateway (TypeScript), at the pre-land check job, before the suite (`run/run-jobs.ts` → `approval/approval-gate.ts`):

- The squash already returns the changed paths (`LandingTree.files`), so path classes cost no Artifacts call; the runner would have needed a protocol change and an image redeploy on deadline day.
- The policy, its parser and the lexer are one TypeScript module the web's Settings page and MCP also import (the owner asked for one shared parse).
- Comment-only needs file contents, which the gateway reads with one `changedFiles` diff only when the policy asks for syntax and every file is judgeable; a triage reads the same diff for its size (once, whichever asks first). The diff goes through the engine's read index (`repo/read-through-port.ts`, doc 31): the stalk side is already there from the warm-up after the last landing, and the bean's side is fetched once and found again by the next warm-up.
- It runs in the job, outside the engine's deterministic reducer: the engine sees an ordinary check result (green, or a red with one failing "test"), so with the rules off every run replays exactly as before (parity and determinism tests unchanged).

The policy is read from the **stalk** head at each judgement (`branchHead('stalk')` plus the file at that commit), never from the bean. A stalk that cannot be read is a retryable job failure, never "no policy".

## 4. Routes

- **Writers.** A bean whose principal is outside a class's `writers` falls off at the pre-land check, the same way a protected path does (`guardRed` in `checks/repository-checks.ts`, one failing "test" `changes a class it may not write`, naming the classes and who may). This extends the protected-paths mechanism rather than adding a second guard: `protected-paths` says "a person who decides, with their own credential"; `writers` says "these principals". Principals: a repository's push is `@<handle>` of the person it acts for; a race's bean is `agent:<slot>` of the sandbox its check runs in.
- **Card.** Held before landing, not before promotion: a held bean's check answers a red `awaits approval by a person` that says nothing needs fixing. Holding before promotion would mean new engine state, timers and inputs in the reducer that races replay, on deadline day; holding before landing reuses the fall-off and re-submit paths the engine already has. An owner or maintainer approves (§5.1); the approval is for the bean's current revision (its pushed head), and a repository's bean waiting for its author is re-submitted at that head at once, so its check runs again and passes. A new push needs a new approval. Races have no approve path (built 2026-10-14 for repositories only: a race's beans have no pushes and no registry record to decide who may approve). The hold's red is marked (`awaitsApproval` on the check result), and a repository engine spends no rework round on it (`v2-landing.ts`, since 2026-10-14): the author's next push or the approval re-submits the bean, so a hold never counts towards `max_rework`. A race still counts it, exactly as before (owner's decision 2026-10-14): nobody pushes or approves there, and the rounds are what end a held race bean; that is why races keep the rules off. What an author does with the red is theirs: the load generator reworks any red, so in the staging benchmark a hold still cost a rework (about 45 s and a re-check), and it does not auto-approve (owner's decision 2026-10-14); only a harness that waits on `awaiting a person's approval`, or a person approving, avoids it.
- **Triage.** Clef (`@cf/cloudflare/clef-flash`, System One body with `model: 'clef-flash'` and one `choice` question `route` with criteria for `auto` and `card`) answers within 2.5 s; otherwise the rule does: `auto` when the bean is also comment-only, docs-only or tests-only, else `card`. Clef holds a bean only when it picks `card` with probability at least 0.65 (`CARD_MIN_PROBABILITY`); a less certain `card` lands on its tests, and the receipt shows `auto (clef, p=<auto's probability>)`. The staging benchmark (`research/race/runs/stg-scion-policy-fastify-16-s*`) showed why: a `card` at p=0.51 held the same bean on every seed with nobody to approve it. The gate asks through `@gitstalk/shared-ask/pick/decision-model` (`askChoice`, `decisionModelFrom`), the module the picker uses; the local adapter it started with was removed on 2026-10-14. Clef only sees class names, paths and the diff's size, never contents.
- **What Clef reads** (`approval/triage-question.ts`): the classes, the deciding class and its `description`, up to 40 paths and the file count, and the merge diff's `lines_added`, `lines_removed`, `test_line_share`, `new_files` and `deleted_files`; never file contents. The criteria say what each route is for: `auto` for comments, docs, tests, type declarations, a contained fix or feature, a behaviour-keeping refactor or a backwards-compatible API addition; `card` for authentication, permissions, secrets, data, money, removed or changed public behaviour, build, CI, dependency or deployment configuration, or a change of several hundred lines across many files; and the tests run either way. Until 2026-10-14 Clef read only the classes and paths, with one-line criteria.
- **One judgement per change.** A triage is reused while its fingerprint is the same: the classes, the policy file's text, and the bean's own change (its pushed revision; in a race, its files). Never the stalk commit the bean merges onto. Before 2026-10-14 the fingerprint held that commit, which moves with every landing, so each re-check asked again: the benchmark made 59 to 64 Clef judgements for 38 beans, and bean t013's first push was answered auto, auto, auto, then card at p=0.51 as prerequisites landed under it (its merge's file list shrank). With the new fingerprint those runs would have asked at most once per push (46 to 51; projected from the push lines, not measured).
- **Evaluation** (`approval/triage-eval/README.md`): a labelled set of the benchmark's 37 triaged beans with Clef's recorded answers, plus synthetic cards; the exact request bodies for the question as run and as now; mocked tests; and `scripts/clef-triage-eval.mjs --live` for the owner to score the real model. The recorded answers already show the other side of the coin: the benchmark's Clef chose `auto` for every bean but t013, including the five the set labels `card` (t006, t007 and t009, changes of 450 to 850 lines; t012 and t019, which change which forwarded headers are trusted; t013 is labelled `auto`; labels confirmed by the owner on 2026-10-14).

### 4.1 Recheck: the intents of beans that landed after the fork (2026-10-15)

Two beans can each pass their tests, merge with no conflict and still break together: one moves `price()` from cents to dollars, the other adds shipping as `+ 500` cents (the `coop/shipping-fee` example). The merged-tree check catches it only when a test covers the combination. Without one, the paths and line counts above give Clef nothing to see, so a triage now also reads intents (owner's decision 2026-10-15: agent first, then a person).

- **What Clef reads, in addition** (`approval/triage-question.ts`): `intent`, the bean's own (its first push's commit message, `PushBean.intent`), and `message`, its latest push's whole commit message without `Intent-checked:` trailers when it says more than the intent (at most 600 characters). And `landed_since_fork`, the beans that landed on the sprout after the bean's fork point (`TaskState.pushedBase`, else its base), newest first, at most 8 (`approval/landed-since-fork.ts`), each with its intent, message, files, `shared_files` and how the two changes connect (`approval/bean-links.ts`, read from the two diffs, the landed bean's being its sprout commit against that commit's parent):
  - `this_imports_theirs` / `theirs_imports_this`: `from -> to`, a file one bean changed imports a file the other changed (relative imports, resolved like `repo/import-closure.ts`);
  - `they_changed_this_uses` / `this_changed_they_use`: names (a function, class, constant or type) around one bean's changed lines that appear on the other's new lines.
    Only beans the bean's author has not marked as checked are listed. A repository engine only: a race has no pushed intents and lists none. With no such beans, the question is exactly the one above, so the recorded evaluation (`triage-eval/requests.jsonl`) is unchanged. The links are a heuristic: one module per language family in `approval/imports/` (the `Language` interface in `language.ts`, registered by extension in `languages.ts`) reads a file's imports and the name a line declares from its text alone, never a build system. Built for JavaScript and TypeScript, Python, Ruby, Java, Kotlin, C#, Swift, Go, Rust, C and C++, and PHP: relative imports exactly, module or namespace imports by path suffix, same-package or same-module files by a type or file name used (Java, Kotlin, Go, C#, Swift), and header to source pairing (C and C++). They point Clef at a contract; they never decide. Known gaps (2026-10-16):
  - Python: a one-word absolute import (`import json`) suffix-matches any `json.py` the other bean changed; `.pyi` stubs and imports inside one-line `if` bodies are not read.
  - Ruby: requires built at run time (`File.join`) and Rails/Zeitwerk autoloading by convention are not resolved.
  - Java and Kotlin: the package is the directory, not the `package` line; lower-case class names, modifier-less constructors and declarations split over lines are missed; Kotlin's package fallback can over-match.
  - C# and Swift: string literals are not stripped (a type name in a string can link); operators, indexers, `init` and `subscript` are not declarations; Swift modules come from directory names, never `Package.swift`.
  - Go: names inside grouped `const (…)`/`type (…)` blocks; `go.mod` is not read, so a vendored copy can tie with the real package.
  - Rust: `#[path]`, 2018-style `use pricing::x` without `crate::`, and `src/bin` layouts.
  - C and C++: angle includes get no header-to-source pairing (on purpose: `<stdio.h>` must not link a project `stdio.c`); `a * price(b);` can read as a declaration; operator overloads are not declarations.
  - PHP: inline fully qualified names (`new \App\X()`) are not imports; matching on the last two namespace parts can over-match common names.

## 5. Receipts and approving a held bean

Every judged bean leaves a `RouteReceipt` in its engine's SQLite (`bean_routes`): classes, route, the deciding class, `by` (`policy`, `clef`, `rules`), Clef's probability, `latencyMs` (how long Clef took to answer, or to fail when the rule answered; null when Clef was not asked, including a reused triage; absent before 2026-10-14), principal, reviewers, a refusal, the approval (`not-needed`, `awaiting`, `approved` by whom), the policy file and stalk commit it was judged by, the revision, the time. Surfaces: the push's `remote:` lines (`approval rules: api -> card (clef, p=0.81)`), the gateway RPC `beanRoute(run, bean)` and the `route` field of `beanDetail`, and the **hold** (`BeanHold`, `shared-race/src/bean-approval.ts`; `gateway/src/approval/bean-hold.ts`) on every pushed bean (`pushedBeans`, `agentBean`): `held` while its latest receipt is `card`, judged its current head, refused nothing and no approval names that head; `approved` once one does; null otherwise. The web's Changes list badges a held bean **Held** (state `held`, violet, the colour of people's decisions, never the red of a failure) with a Held filter, and its page opens with the Held panel. MCP `bean_status` and `bean_wait` add `held: true`, `approve_url` (the bean's page) and a next step that says nothing needs fixing and to tell the person.

The hold is also in the engine's log, so the journeys read it without matching strings: the gate's red carries `held` (`CheckResult.held`: the classes, the deciding class, who decided), and the `preland.check` event repeats it as `held`. Readers of the log treat such a check as a hold, never as a red: the reducer (`shared-ask/src/race/reduce-race.ts`) puts the bean in phase `held` with a `held` step and no rework round, and the next commit of the same head is an `approved` step (the approval's re-submission), while a different head is a new push judged again. The bean page's journey (`web/src/changes/journey.ts`) shows a violet **Held for approval** step with the held panel's mark, the classes and who decided; after an approval, **Approved by @x** with the time and note (`pushedBeans` lists every approval of a bean's revisions as `approvals`), then **Checking <sha> again** and the real result; a push while held reads as a new revision held again. Home's bean journey and the explorer's steps say the same, the Changes row says nothing needs fixing, the push's verdict is `HELD: ... nothing in it needs fixing` instead of `RED` and a fix (`push/push-messages.ts` `heldLines`), a push to `refs/wait/any|all` calls the bean `held` (never `red`), does not count it as waiting for its author's push, and says `next: ask your person to approve <bean> on its page; do not push it again` (`push/wait-messages.ts`, since 2026-10-16; before, it said `is red and waits for your push` and `next: fix`, and agents re-pushed, which needs a new approval), MCP `repo_status` lists held beans apart from those sent back, `bean_status`'s summary leads with the held next step instead of the phase `red`, and `bean_status`'s engine next step for phase `held` says to wait.

### 5.1 Approve: one path

`approveBean(run, bean, { approver, revision?, note?, client, idempotency_key? })` on the gateway's default entrypoint (`approval/approve-rpc.ts`) is the only way to approve. The web's Approve button (a server action, `web/src/server/approval-actions.ts`, behind the usual same-origin, session and CSRF checks) and MCP `bean_approve` (`mcp/src/tools/bean-approve.ts`) both call it. In order:

1. The request is validated (`ApproveBeanRequest`); the engine must belong to a repository in the registry.
2. The approver (a person's account id) must have `decide` on the repository (`mayUseEngine`: the owner and maintainers, an org's owners; archived repositories refuse). A writer gets 403 naming the role; someone who cannot read it gets 404.
3. In the engine (`RunDO.approveBean` → `approval/approve-bean.ts`): an idempotency key used before for this bean replays the first answer; a named `revision` that is not the pushed head is refused as `stale_revision` (409); the bean must be held (409 `invalid_state` otherwise; a new push still being checked says so); an approval of the head that already exists replays; the self-approval rule (§5.2) runs for MCP clients; then the approval is saved for the head (`bean_approvals`, with the note, the client and the key in `bean_approval_notes`) and a bean waiting for its author is re-submitted at that head.
4. A new approval is written to the repository's access log (`repository_audit`, action `bean.approve`: approver, `bean <name> at <sha7>; via web|MCP (<client>); note: …`) and logged.

The answer (`ApprovedBean`) carries the approval (who, when, note, client), the revision, whether the bean was re-submitted, whether it was a replay, and the hold now. The web panel shows it at once and invalidates the page's pushed-beans and events queries, so the live page moves on without a reload; MCP answers the receipt with `approve_url` and the next step (`bean_wait`).

`bean_approve` is registered only for sessions with the `write` scope (`mcp/src/repos/repo-tools.ts`; the role is checked per call by the gateway, as for every write). It refuses a session that does not act for a person: it needs the person (`sub`, the session's user id) and the agent client (`act`, its `agentKey`), and an automation's or Actions job's identity never approves (the gateway would refuse them too, as they are not people with a role). Its description tells agents that approving is their person's decision: call it only when the person explicitly asked, never on their own initiative and never to unblock their own work. The tool surface stays at most 30 tools per caller (a test asserts it): a `write` session has 28, `write` and `secrets` 30.

### 5.2 The self-approval rule (a safety property)

A card means "a person approves this". An agent that pushed a bean and then approves it would turn that into "the agent approves itself", so: **an approval from an MCP session is refused (`self_approval`, 403) unless the person passed `confirm_owner_intent: true`, when the bean's latest push was made for the same person and the gateway cannot show that a different agent session made it** (`approval/self-approval.ts`).

To tell sessions apart, every push records its credential (`ProtectedAccess.pusher`, beside `who`): `oauth:<client id>` for an MCP session token minted by `git_credentials` (the OAuth client the token was minted for) and for `bean_commit` from an OAuth session; `web` for a web editor save; `personal-token:<id>`, `ssh-key:<id>`, `deploy-token:<id>` for those credentials; `engine` for engine and job tokens; null for beans stored before. The caller's session is `oauth:<client id>` for an OAuth grant and `token` for a personal token used as the bearer.

- Shown to be another session, so allowed: a push by someone else; a web editor save (the person in a browser); a push or server commit by a different OAuth client's session.
- Not shown, so refused without the confirmation: the same OAuth client (sessions of one client are not told apart: conservative); the person's SSH key or personal token, because an agent on the person's machine pushes with exactly these; an MCP session without a known client; a credential that was not recorded.
- The web's Approve button is the person and is never refused by this rule; `confirm_owner_intent` is only for MCP, and the tool's description says to set it only after the person confirmed.

Why fail closed: the cost of a false refusal is one more message to the person (the refusal carries the bean's page, where they approve themselves); the cost of a false allow is an agent landing its own sensitive change. Why not refuse every same-person bean: a person who pushed by hand and asks their agent to approve, or two agents of different clients reviewing each other's work for one person, are legitimate and visible in the audit log.

## 6. Turning it on

`approval_rules` in the run config (`shared-race/src/run-config.ts`, `approvalRulesOf`): absent means on for a repository engine reading its own checks (new repositories; with no policy file nothing changes) and off for races and engines with an operator's suite. No preset (`demo`, `v24`) sets it, so published race numbers are unchanged. A race opts in with `"approval_rules": true` in its `POST /v1/runs` body; a repository engine can set it in `settings.engine` when opened.

## 7. Settings → Approval rules

`/<owner>/<repo>/settings/rules`: the YAML in the builder's editor pane (a repository without a file opens on the recommended starter, `STARTER_POLICY` in `policy-file.ts`: comments, docs, tests and lockfiles `auto`; migrations and auth paths `card`; everything else `triage` through the fallback class `everything-else`; nothing changes until it is saved). Until the fallback class (2026-10-14) the starter listed source roots (`src/`, `lib/`, `app/`, `packages/`, `pkg/`, `cmd/`, `internal/`) for `triage`, since a catch-all paths class would also have matched docs and tests and the strictest route wins; a change outside those roots then landed untriaged. An agent's change to `.gitstalk/` is held by the built-in `policy-change`, so the starter has no class for it (one would also hold a maintainer's own save). The text is validated as you type by the same `readApprovalPolicy` the engine runs (same messages, line numbers). Owners and maintainers save; everyone else reads, with why. A save goes through the one server-side commit flow that `bean_commit` and the automation builder use (doc 33; `automations/editor-rpc.ts` `pushSave` → `RunDO.repoSaveFile` → `commit/file-save.ts` → `commit/server-commit.ts`): the engine validates the path and size, commits the new text on the latest landed commit, authored by the signed-in person (trailers `Actor: @<handle>`, `Via: Settings → Approval rules`), pushes it as a new `bean/rules-<short>` by compare-and-swap (it must not exist) and submits it like any push. The page sends an idempotency key made once per save attempt, so a double click or a retried request makes one bean; it lands through the pre-land check, and the page shows the commit and follows the bean until it lands. Since the person may decide and saved with their own identity, the bean is not held for a card. RPC: `rulesSource`, `saveRules`, `rulesBean` (`shared-race/src/rules-editor.ts`); `policyGet(run, ref?)` returns the parsed policy on the stalk (or a ref), its commit and its problems.
