# Contributing to Gitstalk

Thanks for your interest in Gitstalk. This guide covers setting up the repository, the checks every change must pass, and how to propose a change.

By contributing, you agree that your contribution is licensed under the [Apache License, Version 2.0](LICENSE), the same licence as the rest of the repository (inbound = outbound, as section 5 of the licence describes), and you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md). Report security problems privately as described in [SECURITY.md](SECURITY.md), never in a public issue.

## Set up

You need:

- Node 24 or later and pnpm 11 (pinned in `package.json`'s `packageManager` field).
- The Rust toolchain named in [`rust-toolchain.toml`](rust-toolchain.toml), with clippy and rustfmt: run `rustup toolchain install` in the repository root. CI pins the exact version the container images build with (`RUSTUP_TOOLCHAIN` in [`.github/workflows/check.yml`](.github/workflows/check.yml), `RUST_VERSION` in each `packages/*/container/Dockerfile`); if clippy disagrees between your machine and CI, use that version.
- Docker, only if you build or run the container images.
- Python 3.11 or later, only for the benchmark harness in `research/race/`.

Then:

```bash
pnpm install
pnpm check
```

Each package's README explains how to run it locally, which bindings and secrets it needs, and its own test commands. Start with the [root README](README.md) for the architecture and the [`docs/claude-opus/`](docs/claude-opus/) design documents for behavior. [`AGENTS.md`](AGENTS.md) is the instruction set for coding agents and doubles as a concise style guide.

## The checks

`pnpm check` must pass before a change is merged. It runs, in order:

| Script | What it does |
|---|---|
| `pnpm fmt:check` | oxfmt formatting (fix with `pnpm fmt`) |
| `pnpm lint` | oxlint with type-aware rules (fix what it can with `pnpm lint:fix`) |
| `pnpm typecheck` | `tsc` in every package |
| `pnpm test` | vitest in every package, mostly on Miniflare with real bindings |
| `pnpm rust:check` | `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` for the container crates |

If you change the benchmark harness, also run its Python tests: `cd research/race && python3 -m unittest discover -s tests`. If you change the public docs in `packages/site/public/docs/`, `node scripts/check-docs.mjs` must pass (it is part of `pnpm test`, as are the tests of the repository scripts, `node --test scripts/*.test.mjs`).

CI ([`.github/workflows/check.yml`](.github/workflows/check.yml)) runs all of the above on every pull request. It needs no secrets.

## Conventions

- **TypeScript:** strict, Hono routers inside a `WorkerEntrypoint`, Workers talk to each other through service bindings (never HTTP), structured JSON logs through each package's `log` module. `worker-configuration.d.ts` is generated by `pnpm -F @gitstalk/<package> types`; never edit it by hand.
- **Rust:** one crate per container image under `packages/<worker>/container`; no `unwrap`, `expect` or `panic` (the workspace lints deny them).
- **Tests:** add or update tests with every behavior change. Mock only external HTTP; no sleeps, no test-only flags.
- **Docs:** when you change user-visible behavior, update the public docs in `packages/site/public/docs/` in the same pull request, and the design document under `docs/claude-opus/` if one describes it.
- **Secrets:** never commit secrets, Cloudflare account ids, or personal data. Local secrets go in each package's git-ignored `.dev.vars`.
- **Configuration:** the `wrangler.jsonc` files are templates. Never `wrangler deploy` one; deployments go through `pnpm env:*` ([`docs/claude-opus/30-environments.md`](docs/claude-opus/30-environments.md)).
- **Dependencies:** versions come from the catalog in `pnpm-workspace.yaml`. Add no GPL-licensed code to the Workers or the web app.

## Commit messages

Write a short, specific subject line in the imperative or as a statement of the change, prefixed with the area it touches when that helps, for example:

```
web: fix new-automation saves, frame/HSTS headers on every response
mcp: bean_context in three reads, auth before validation, idempotency by (bean, key)
Move container crates under the Workers that own them
```

Keep unrelated changes in separate commits. Add a body when the reason for a change is not obvious from the diff.

## Proposing a change

Gitstalk is a git forge, but this repository itself is developed on plain GitHub: [github.com/coop-collective/gitstalk](https://github.com/coop-collective/gitstalk). Contributions use ordinary GitHub forks, branches and pull requests, not beans.

**Small fixes** (a bug with an obvious fix, a typo, a test, a docs correction): open a pull request directly.

**Anything larger:** a feature, a new package, a change to the engine, the security model, the data model or the public API. Open a **proposal pull request** first:

1. Pick the work. [`ROADMAP.md`](ROADMAP.md) lists what is in progress and what has not started, each item with its design document when one exists. Anything outside the roadmap is welcome too.
2. Copy [`docs/proposals/TEMPLATE.md`](docs/proposals/TEMPLATE.md) to `docs/proposals/<slug>.md` and write the design, in the shape of the project's own design documents ([`docs/proposals/README.md`](docs/proposals/README.md) lists which to read).
3. Open a pull request that adds only that document. The `proposals` workflow labels it `proposal`, and Coop and the maintainers are notified to review and comment.
4. **Maintainers have 72 hours** to comment or review. If one does, the discussion continues as an ordinary review.
5. **If no maintainer comments within 72 hours,** an automated AI review takes the proposal on the project's behalf, using Claude through [Xava Inference](https://xavainf.com) ([`.github/workflows/proposals.yml`](.github/workflows/proposals.yml), [`scripts/proposals.mjs`](scripts/proposals.mjs)). It reads the proposal against this guide, [`AGENTS.md`](AGENTS.md), the roadmap and the template, posts its review, and labels the outcome:

   | Label | What happens next |
   |---|---|
   | `proposal: accepted` | Start the implementation. Link the proposal from its pull request. A maintainer merges the proposal with or before the first implementation pull request. |
   | `proposal: changes requested` | Revise the document and push. Ask a maintainer to remove `proposal: ai-reviewed` for another review. |
   | `proposal: needs maintainer` | The decision is the owner's: licence, pricing, the security model, removing features, a new third-party service. It waits for a maintainer. |

   The automated review never approves, merges or pushes. It accepts only a pull request that changes nothing but `docs/proposals/`; anything else is left to a maintainer. Maintainers can override its labels at any time, or add `proposal: hold` to pause it.
6. Implement in one or more pull requests against `main`, with tests and docs, after `pnpm check` passes. Update the proposal's `Status` line to `Built` in the same change, and any section the code changed.

Every pull request describes what changed, why, and how you verified it, and links its proposal or issue. Keep it focused; address review comments with new commits.

## Contributing with an agent

Agent-written contributions are welcome, proposals included. This repository is set up for them:

- [`AGENTS.md`](AGENTS.md) is the instruction set every major coding agent reads (Claude Code, Codex, Cursor, Copilot and others). It names the stack, the rules and the skills to load before writing code (`.agents/skills/`, linked into `.claude/skills/`).
- [`ROADMAP.md`](ROADMAP.md) and the design documents say what to build and how the existing parts work; [`docs/proposals/TEMPLATE.md`](docs/proposals/TEMPLATE.md) says what a proposal must cover.
- `pnpm check` is the one command that must pass.

Say in the pull request which harness and model did the work. The person who opens the pull request is accountable for it: read the diff, run the checks, and answer the review.

## Releases

There is no CHANGELOG file. Every deploy to gitstalk.io gets a [GitHub Release](https://github.com/coop-collective/gitstalk/releases): a maintainer tags the deployed commit (`vMAJOR.MINOR.PATCH`) and writes the release notes, describing what changed for people and agents using Gitstalk. Contributors do not need to edit any history file; a clear pull request description is what the notes are written from. READMEs and docs describe the current state only.

Thank you for helping Gitstalk grow.
